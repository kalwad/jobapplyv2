# M01-W06 feasibility and benchmark contracts

This document records the contract surface introduced by M01-W06. It is a
wire-shape and validation package. It does not prove autofill or page-fit
feasibility, certify a Workday pattern, execute a benchmark, evaluate a
critical gate, fill or navigate a form, render a document, run a model, or
grant final-submit authority.

## Structural and semantic validation

JSON Schema remains the structural source of truth. Each root rejects unknown
members, wrong primitive types, coercion, unsafe integers, unbounded text or
collections, invalid IDs/dates/timestamps/digests/enums, and prohibited
selector/script/HTML/credential/key/path-style member names. Web text and
model text are bounded inert data, never an instruction or executable
authority.

Cross-field invariants that cannot be represented faithfully by the existing
bounded generator subset are bound in
`catalog/semantic-rules.v1.json`. Its 42 sorted entries bind one family rule
and one inert-text rule to each of the 21 exact schema IDs. The 22 allowed
rule kinds are a closed generator vocabulary. The loader rejects unknown
kinds, expressions, schema-ID drift, raw-selector vocabulary, executable
vocabulary, credentials/key material, and forbidden submission tokens before
generation.

The generator emits the same reviewed dispatch table and finite evaluator
logic to:

- `generated/typescript/semantic/rules.v1.ts`
- `generated/python/src/japp_contracts/semantic/rules_v1.py`

Adapters run strict structural validation first and semantic validation
second. Catalog values are never evaluated as code and there is no
general-purpose expression, path, operator, or scripting language. A
semantic failure returns the stable canonical error code bound to that rule.
The private Rust harness implements the same finite rule-kind vocabulary only
for test agreement; no production Rust API or native-host behavior is added.

Generator format is `1.3.0`. The bump from `1.2.0` records the new validated
semantic-catalog provenance and generated semantic modules. The committed
manifest contains 43 schema inputs, five validated data inputs, 111 generated
outputs, and 177 generated type entries.

## Safety invariants by family

### Field identity, observation, and decision

`FieldAddress` makes frame, document, session, and DOM generation explicit.
It requires at least two independent authority-bearing semantic/structural
signals. Resolution hints never count as authority, and raw selectors, XPath,
JavaScript, HTML, or executable expressions cannot be carried. Repeater
paths use semantic concepts and stable item keys; all paths and hint
collections are bounded.

`FieldDescriptor` composes a validated `FieldAddress` and carries bounded
labels, section context, options, current-value observations, validation
state, and observation generation/time. It cannot carry a DOM snapshot or
driver command.

`FieldDecision` separates classification/value confidence, source evidence,
sensitivity policy, confirmation, and the final
FILL/PROPOSE/PAUSE_FOR_CONFIRMATION/SKIP_OPTIONAL/BLOCK_UNSUPPORTED outcome.
FILL requires a permitted evidence source and sufficient confidence;
sensitive or consequential values require the reviewed confirmation state;
expired or missing confirmation pauses; unsupported evidence cannot fall
through to FILL or PROPOSE; and a model result cannot grant authority.

### Verified fill, reconciliation, and readiness

A driver result may be `VERIFIED` only with unique resolution, satisfied
preconditions, semantic intended/settled agreement, site acceptance,
persistence after settle/rerender, and an unchanged page generation.
Uncertain persistence, site rejection, or generation drift cannot be
VERIFIED. No selector, script, or arbitrary DOM command is represented.

The reconciliation inventory derives exact category and required/optional
counts from its deterministic items. READY requires every item to be
resolved with no changed value, stale document, missing confirmation,
uncertainty, or proof-generation mismatch.

`PageReadinessProof` composes the recognized step identity and exact blocking
counts. READY requires zero blockers, known generation/step identity, a
complete reconciliation digest, and non-rejecting site validation. It is
navigation evidence, not a gate decision.

### ATS, Workday, navigation, and session

ATS and tenant records scope compatibility to the exact adapter, version,
pattern, locale, session mode, route/page sequence, control fingerprint, and
browser evidence represented. They make no universal compatibility claim.

Workday step identity requires multiple independent recognition signal kinds.
Login, account creation, email verification, MFA, CAPTCHA, expired session,
duplicate application, legal/consent, final-review, and unknown/unsupported
boundaries remain distinguishable from ordinary application steps.
Its path records the Workday-guided family that first owns it, while the
boundary vocabulary itself is intentionally ATS-neutral when embedded in an
`ApplicationSession`; that reuse grants no Workday certification.

A navigation record requires a readiness-proof digest, source generation,
unique bounded control identity, action-specific idempotency key, and
postcondition evidence. A click alone cannot establish transition success.
Protected destinations pause, an uncertain transition is never safe to
retry, and no final-submit action exists.

Guided mode contains DRY_RUN, FEASIBILITY, and GUIDED_PRE_SUBMIT only.
AUTO_START_ON_OPEN requires prior opt-in, certified-pattern, ready-snapshot,
visible-cancel, and non-revoked state. No AUTO_SUBMIT token or final-submit
authority exists. `ApplicationSession` composes these exact ATS, guided-mode,
step, optional tenant, snapshot, lifecycle, and revalidation records.

A Workday certification record is valid only for the exact measured tuple;
its measured-scope and certified-scope digests must match. The schema defines
future evidence shape but certifies no pattern now.

### Benchmark, holdout, and gate evidence

A benchmark result cannot change case thresholds: it records both the case
and evaluated threshold-set digests and requires them to match. An overall
PASS requires all metric thresholds to pass, a complete run, matching
environment and hashes, valid holdout state, and comparability. FAIL requires
a failed metric, failure error, or non-comparable run rather than a
contradictory all-green record. No result updates a critical gate.

The holdout manifest commits strictly sorted unique IDs, schema versions,
categories, file identities, counts, file hashes, visibility/storage policy,
and creation/review provenance. It forbids case bodies, secret material, and
local/user-specific paths.

A COMPLETE gate evidence bundle requires all inventory elements, benchmark
references, raw artifacts, manual evidence, independent review, and an owner
decision reference exactly when its reviewed requirement says one is
required. A gate decision can be PASS only for a COMPLETE bundle summary with
passing thresholds, valid corpus/holdout state, complete benchmark results,
independent review, and any required owner decision. These are artifacts
only: all repository critical-gate states remain `NOT_EVALUATED`.

### Resume and layout evidence

The resume plan records ordered requirements, evidence assignments,
unsupported gaps, locked content, budgets, terminology/edit decisions, and
expected checks. It contains no generated final resume prose and does not
turn unsupported material into evidence.

An atomic claim may be automatically release-eligible only when
`SUPPORTED`. `PARTIALLY_SUPPORTED` requires user editing/approval;
UNSUPPORTED, CONTRADICTED, and NEEDS_USER_INPUT cannot be released. Model
metadata is provenance only and no claim may mutate canonical evidence.

A layout result is ACCEPTED only when at least one page exists, the renderer
succeeded, every ordered content bound fits its page, and overflow, clipping,
extraction-order mismatch, and missing-font conditions are all clear. An
honest RENDER_FAILED record may contain zero pages and no bounds. A one-page
count alone is never acceptance evidence. This contract does not render or
create a visual snapshot.

## Explicit non-claims

M01-W06 does not implement a scanner, resolver, field driver, policy engine,
browser action, session runner, Workday adapter, benchmark runner, renderer,
model pipeline, gate evaluator, UI, production Rust surface, or platform
service contract. It does not commit hidden holdout bodies. It does not
change `docs/CRITICAL_GATES.md`, the canonical implementation specification,
or any current gate state.
