# M01-W07 cross-platform capability and platform-service contracts

This document records the contract surface introduced by M01-W07. It is a
wire-shape and validation package. It does not detect a platform, certify a
platform, resolve a path, open a secret store, spawn or terminate a process,
register or remove a native-messaging host, locate or launch a browser,
detect or run a model runtime, install, update, roll back, or uninstall
anything, produce a certification bundle, or evaluate a critical gate.

## Canonical inventory

Nineteen closed Draft 2020-12 roots plus one definitions-only vocabulary.
All roots have path-derived stable IDs, explicit v1 schema versions, bounded
members, no defaults, and catalog-local references only.

`urn:japp:schema:platform:vocabulary:v1` is the definitions-only supporting
document. It declares the certified target and support-tier vocabularies, the
capability families and availability states, the finite platform reason
codes, path roles and the sanitized path-reference grammar, browser and
channel vocabularies, secret roles and opaque references, process profiles,
arguments, stdio and lifecycle modes, registration operations and states,
packaging and update vocabularies, runtime families and accelerators,
diagnostic severity and results, evidence artifact kinds and machine classes,
and the shared `capabilityState`, `supportClaim`, `requestContext`, and
`artifactIdentity` records.

### Specification target identifiers

The repository enum grammar is UPPER_SNAKE_CASE, so the specification's
`macos-arm64`, `windows-x64`, and `ubuntu-x64` targets appear as
`MACOS_ARM64`, `WINDOWS_X64`, and `UBUNTU_X64`. The correspondence is exact
and one-to-one. `UNSUPPORTED_TARGET` is a recognized but uncertified target
and `UNKNOWN_TARGET` is an unrecognized or unevaluated one; neither can ever
carry a certified reviewed tier.

## Structural and semantic validation

JSON Schema remains the structural source of truth. Each root rejects unknown
members, wrong primitive types, coercion, unsafe or out-of-range integers,
unbounded text or collections, invalid IDs/dates/timestamps/digests/enums, and
prohibited executable, credential, selector, script, registry, or path-style
member names.

Cross-field invariants that the deliberately bounded generator subset cannot
express are bound in `catalog/semantic-rules.v1.json`. Its entries grow from
42 to 80: each of the nineteen platform roots gains one family rule and one
inert-text rule, using eighteen new finite rule kinds (`installer-state` and
`update-state` share `PLATFORM_PACKAGE_STATE_EVIDENCE`). The closed generator
vocabulary grows from 22 to 40 kinds. The loader still rejects unknown kinds,
expressions, schema-ID drift, raw-selector vocabulary, executable vocabulary,
credentials or key material, and forbidden submission tokens before
generation. Structural validation always runs first; catalog content is never
evaluated as code.

## Safety invariants by boundary

### Platform identity and support claims

A support tier is never self-asserted. `supportClaim` separates the claimed
tier from the reviewed tier and requires, for any certified reviewed tier: a
certified target, `REVIEW_COMPLETE`, an evaluated commit and tree, a reviewer
identity, and at least one evidence reference. An uncertified record must
carry a finite reason, and only a measured native run can support
certification. No contract in this package certifies any platform; every
committed representative is `UNSUPPORTED` or explicitly labelled a synthetic
wire example.

Detected architecture must agree with the detected target. All five roots that
carry both `platform_id` and `architecture` — `certification-input`,
`evidence-record`, `installer-state`, `target-identity`, and `update-state` —
share one binding derived from the specification §5.14.1 certified matrix:
`MACOS_ARM64` requires `ARM64`, and `WINDOWS_X64` and `UBUNTU_X64` require
`X86_64`. No root is exempt. The three roots whose `platform_id` accepts an
uncertifiable target deliberately leave that target's architecture unbound, so
an honest `UNKNOWN_TARGET`/`UNKNOWN_ARCHITECTURE` observation stays
representable; `installer-state` and `update-state` accept only certified
targets and are therefore always bound.

### Capability reporting

A capability report carries exactly one state for each of the eight
specification-owned families. An `AVAILABLE` capability requires provider
identity, version, and evidence and carries no reason; every other state
requires at least one finite reason; `NOT_EVALUATED` requires the matching
evaluation method and the `EVALUATION_NOT_RUN` reason, so an unevaluated
capability is never silently treated as success. A certified tier requires the
five mandatory core capabilities to be available **through a measured native
run**, so a declared plan or a synthetic fixture can never carry a
certification, exactly as the sibling target-identity rule already requires of
the identical `supportClaim` record. **A missing, unevaluated, or
unavailable local-AI runtime never downgrades the deterministic core tier** —
`CERTIFIED_CORE` deliberately imposes no `MODEL_RUNTIME` requirement, while
`CERTIFIED_FULL` requires an available runtime and a referenced profile.

### Paths

A request selects a role and bounded normalized segments. Absolute paths,
traversal, UNC and device paths, drive letters, registry paths, shell and
environment expansion, executable lookup input, and arbitrary working
directories are structurally unrepresentable. A trusted resolution is a
different contract: it reports a location only as an angle-bracketed
role-anchored reference plus a digest, the placeholder must match the declared
role, and any non-resolved state carries no location at all. That privacy
guarantee is independent of what was observed: a `DENIED_PERMISSION` result may
report that the location exists — a permission error is itself that observation —
while remaining non-writable, naming `PERMISSION_DENIED`, and never disclosing
where it is. A `NOT_EVALUATED` or `UNAVAILABLE` result observed nothing and says
so. System scope is
reachable only for the native-host registration role.

### Secret store

Operations are typed over four reviewed key roles. Plaintext secrets,
passphrases, key material, keychain service or account names, Windows registry
locations, D-Bus requests, filesystem paths, and environment-variable
fallbacks have no representation. A retrieval returns only an opaque
`secref_…` reference plus a digest. Store availability and permission state
are always explicit; an unavailable store can never return material. The
`VERIFICATION` profile may only probe availability. External-provider tokens
are deliberately absent and remain future work; no contract reads or writes an
unrelated credential file.

### Process supervision

A plan names an approved executable profile, never command text, an
interpreter, an executable path, or a script body. Arguments are an
already-separated bounded array whose grammar excludes whitespace, quoting,
redirection, chaining, substitution, path separators, and leading dashes; a
semantic rule additionally refuses the reviewed interpreter vocabulary and the
privilege-escalation launchers even when each token satisfies the grammar, and
it refuses them in their executable-suffix spelling too, so `cmd` and `cmd.exe`
are the same refusal. That vocabulary is exactly the ten interpreter tokens and
five privilege launchers the rule names; it is deliberately not an open-ended
interpreter denylist, and widening it belongs to the package that first spawns a
process. The environment is a closed allowlist of six reviewed identifiers whose
values are checked, not merely shaped: the service port must be a real port
number, the path role must be a member of the closed `pathRole` vocabulary other
than the registration role the same rule refuses on the working directory, and
the service bind host must be loopback (`REQ-PLAT-003`). The bounded token
grammar cannot begin with a colon, so the compressed `::1` spelling of the IPv6
loopback address is structurally unrepresentable and only its expanded form is
accepted. Parent-environment inheritance must
be false, the working directory is a typed role, and the executable digest is
mandatory so a substituted binary can be refused. Raw file descriptors,
signal values, and privilege escalation are unrepresentable; termination is a
typed intent. Handles are opaque and are not operating-system process
identifiers. Nothing is spawned.

Native-message framing is bound to the one channel pair that carries the
protocol. Specification §5.14.5 places the length-prefixed protocol on the
native host's binary stdin and stdout, so a `NATIVE_MESSAGING_HOST` plan must
frame exactly those two channels and must leave `stderr_mode` unframed, and no
other profile may use `BINARY_LENGTH_PREFIXED` on any of the three
schema-required stdio channels. The specification does not mention `stderr`
anywhere; this rule takes the narrow reading that a diagnostic channel never
becomes a second protocol stream unless the specification requires it, and it
rejects strictly more than the previous rule did.

### Native messaging

An intent binds a certified target, Chrome stable, a strictly sorted reviewed
extension allowlist, host identity and version, installation scope, the typed
registration location role, and the expected manifest and binary digests.
Length-prefixed binary stdio is mandatory so Windows newline translation
cannot corrupt messages. Arbitrary registry keys, manifest bodies, executable
paths, shell commands, and unreviewed or wildcard extension identifiers are
impossible. No registry, manifest, browser, or filesystem modification occurs.

`observed_state` is the registration state observed **after** the operation
ran; it is never a claim that the operation succeeded. Success is carried by an
empty `reason_codes` instead. A result reports the terminal state its operation
is defined to reach: `REMOVE` reaches `ABSENT` and every other operation reaches
`PRESENT_VALID`.
Because specification §5.14.5 makes all five operations idempotent, a repeat
that already observes its terminal state is still a success and simply reports
`changed: false`. Zero reason codes is exactly a success claim, so it is
admissible only in that terminal state and only when repeating the intent is
guaranteed to be a no-op. A verify operation can never report a mutation; a
valid registration must observe the manifest identity it claims; an absent or
unevaluated registration can never report one; an identity verdict carries the
identity evidence it is about, so `MISMATCHED_IDENTITY` reports the observed
manifest digest and `PRESENT_STALE` the observed host version; and the
identity-mismatch and evaluation-not-run reasons each name the one state they
explain and never appear without it. A removal refused by the operating system
therefore observes `PRESENT_VALID` with `changed: false` and a finite reason,
which is an ordinary explained failure rather than a false success: all thirty
operation/state cells are reachable, and the complete five-operation by
six-state matrix is asserted from reviewed representatives in
`test/schema/w07-platform-rule-matrix.test.ts`. An intent must additionally
carry the `max_message_bytes` limit that specification §5.14.5 makes mandatory
on every platform.

### Browser locator

Discovery names a reviewed family and channel; it cannot name an executable,
search a path, launch a URL, invoke a shell, or pass arguments. A record may
be marked certified only for measured Chrome stable on a certified target with
an available native-messaging capability and a last-tested date. The
vocabulary deliberately cannot express Firefox, Safari, ChromeOS, ARM Windows,
Intel macOS, or another Linux distribution as certified.

### Model runtime

A profile carries the exact artifact digest, runtime family and version,
accelerator and driver bounds, context, quantization, memory requirements,
license and provenance, four measured evidence references, and the
deterministic-core fallback behavior. Acceptance requires a certified target,
availability, complete evidence, and no outstanding reason; an unaccepted
profile cannot claim full AI capability. Accelerator, runtime family, and
target must agree **in both directions**: the certified macOS target is Apple
Silicon arm64 and the §5.14.6 profile list names no macOS CUDA profile, so an
accelerator is bound away from a target it cannot exist on as well as toward the
one it requires, and a CPU-only profile declares neither a VRAM nor a driver
bound. Runtime capability requires accepted profiles to be a subset of available
profiles and preserves deterministic core behavior in every state. `AVAILABLE`
and `DEGRADED_LIMITED` are the two non-blocking availability states, so they are
the two that may report a detected runtime identity and enumerate available
profiles: specification §5.14.1 defines `CERTIFIED_CORE` as AI unavailable **or
below the performance tier**, and a below-tier runtime is detected, not absent.
An empty `reason_codes` and a non-empty `accepted_profile_refs` are each exactly
`FULL_AI_AVAILABLE`, which additionally requires an available runtime on a
certified target. Whether an accepted profile may itself sit below the
performance tier is deliberately undecided here and is recorded as KI-0026 for
M05-W13. No Windows or Ubuntu profile is accepted, the model lock is
unchanged, and nothing downloads, invokes, or selects a model.

### Installer, updater, diagnostics, and evidence

Package states bind identity, version, target, format, artifact digest,
signature state, channel, scope, interruption and recovery, user-data
preservation, and native-host cleanup. The package format is bound to the
certified target from specification §5.14.8, and an installed update must be the
update that was offered. `interrupted` is **historical** — it records that this
operation was interrupted at some point — while `recovery_completed` records
that the interruption was resolved and is meaningless without one; the
_unresolved_ outcome is carried by the `INSTALL_INTERRUPTED` and
`UPDATE_INTERRUPTED` states, never by the flag alone. A successful operation
requires a valid signature, preserved (or explicitly deleted) user data,
evidence references, and no outstanding reason — where a recovered interruption
is not outstanding, so exactly the historical `INTERRUPTED` reason may remain
and specification §5.14.8's required interrupted-update recovery is reportable
as the success it is. No installer command, script, registry modification,
download URL, network request, or signing key is representable.

A diagnostic cannot report success while carrying a blocking reason, cannot
attach a user-visible message to a forbidden-capture record, is never filed as
informational when it blocks a capability, and reports only its own component's
capability family — `PLATFORM_CAPABILITIES` is deliberately unbound because the
aggregate reporter legitimately reports on any family. Evidence records are
synthetic-only and reference every artifact by digest. `machine_class` records
_where_ an artifact was produced and `evaluation_method` records _how_; the two
axes are independent, so a hosted CI runner and a physical development machine
may each execute synthetic fixtures, static inspection, or a measured native
run, and only a synthetic machine cannot execute a native run. A measured native
run requires an operating-system version and build, a certified target, and — on
a hosted runner — the runner image that produced it; a runner image identifies a
hosted runner and nothing else. `NOT_EVALUATED` and `DECLARED_PLAN` are never
measured evidence, so neither reports a passing result, an unevaluated record
observes no operating-system build, and an artifact whose signature did not
verify is never a passing evidence element. An owner decision that precedes a
completed review is refused. Certification input derives inventory completeness
from its required and present evidence kinds, requires that a certified proposal
actually name the evidence it required, and requires a recorded owner decision
before any certified proposal. Raw secrets, unrestricted logs, raw local paths, complete
environment dumps, registry exports, and machine-specific identity are
unrepresentable throughout.

## Authority

M01-W04 already declares the four platform capability and command categories
with empty supported-profile sets and zero allow rows. M01-W07 defines what
those future operations will carry, **not who may call them**: the capability,
command, and authorization-policy catalogs are unchanged, all 127 positive
allow rows and every existing negative case are preserved, and every current
profile still denies every platform command.

Inside the contracts themselves, `requestContext` binds each caller-facing
request to an authenticated principal and profile, and the semantic layer
restricts platform requests to the `ORCHESTRATOR` and `VERIFICATION_HARNESS`
principals under the `PRODUCTION_NO_SUBMIT` and `VERIFICATION` profiles. That
matches the reviewed M01-W04 catalog non-goals exactly: content scripts,
service workers, model runtimes, the public index, the desktop app, the native
host, and the platform adapter itself can never originate a platform request.

## Generator

Generator format is `1.4.0`. The bump from `1.3.0` records that the built-in
finite semantic-rule vocabulary grew by eighteen platform rule kinds, so the
emitted TypeScript and Python evaluator modules contain new generator-owned
logic rather than only new data rows. No IR construct, emitter shape, manifest
field, or naming rule changed. The committed manifest contains 63 schema
inputs, five validated data inputs, 152 generated outputs, and 256 generated
type entries.

## Explicit non-claims

M01-W07 implements no platform adapter, secret store, process supervisor,
native-messaging registrar, browser locator, model runtime, installer,
updater, or diagnostics collector. It certifies no platform, accepts no model
profile, publishes no compatibility row, creates no evidence bundle, and
changes no critical-gate state: `AUTOFILL_FEASIBILITY`,
`RESUME_PAGEFIT_FEASIBILITY`, `WORKDAY_GUIDED_PRE_SUBMIT`, and
`CROSS_PLATFORM_CORE` all remain `NOT_EVALUATED`. It grants no new operational
authority, adds no product, UI, or provider behavior, and does not change the
canonical implementation specification.
